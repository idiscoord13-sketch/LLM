## ۰. خلاصه‌ی اجرایی

**واقعیت بی‌تعارف:** ساختِ یک مدل ۷B «از صفر» (pre-training from scratch) برای یک فرد **واقع‌بینانه نیست** — در بخش ۱ محاسبه کرده‌ام که یک 7B مدرن (آموزش روی ~۱۵ تریلیون توکن) حدود **۴۰۰٬۰۰۰+ GPU-hour روی H100** و صدها هزار دلار هزینه می‌خواهد. کاری که واقعاً «مدل مال خودت» می‌سازد و هم‌زمان یادگیری عمیق می‌دهد، **ترکیب دو مسیر** است:

- **مسیر A — یادگیری (ارزان، چند روز):** یک مدل کوچک (~۱۰M تا ~۵۰M پارامتر) را از صفر بساز: tokenizer، معماری Transformer، pre-training، SFT. هدف فقط فهمیدن است، نه محصول. هزینه: چند ساعت تا یک روز روی یک GPU اجاره‌ای (<۵ دلار).
- **مسیر B — محصول (مسیر اصلی تو):** یک **base model باز و خوب** (پیشنهاد من: خانواده‌ی **Qwen3** با لایسنس Apache-2.0) را بردار و با **post-training** (SFT → DPO، بعداً KTO برای فیدبک کاربران) ارتقا بده. مدل واقعاً «مال تو» می‌شود چون وزن‌ها و لایسنس اجازه‌اش را می‌دهند و تو آن را روی داده‌ی خودت تخصصی می‌کنی.

**چرا نه pre-training کامل؟** چون ارزش افزوده‌ی تو در *داده* و *post-training* و *data flywheel* است، نه در سوزاندن میلیون‌ها دلار برای بازساختن چیزی که Qwen/Google/Meta رایگان داده‌اند. `[فرض یا استنتاج من، مبتنی بر محاسبات بخش ۱]`

## ۱. مفاهیم پایه و استراتژی کلی

### ۱.۱ تعریف دقیق هر مرحله (هر اصطلاح، اولین بار)

- **Pre-training (پیش‌آموزش):** آموزش مدل از صفر روی حجم عظیم متن خام با هدف «پیش‌بینی توکن بعدی» (next-token prediction). خروجی: یک **base model** که زبان و دانش عمومی دارد ولی دستور نمی‌فهمد. گران‌ترین مرحله.
- **Continued Pre-training (CPT / پیش‌آموزش ادامه‌دار):** برداشتن یک base model آماده و ادامه‌ی pre-training روی داده‌ی حوزه/زبان خاص (مثلاً متن فارسی زیاد) تا دانش پایه‌اش را به سمت تو ببری. **این مسیرِ تقویت فارسی است، نه from scratch.** `[رایج در صنعت]`
- **SFT (Supervised Fine-Tuning / تنظیم نظارت‌شده):** آموزش روی جفت‌های «دستور → پاسخ خوب» تا مدل یاد بگیرد دستور را دنبال کند و مثل دستیار جواب دهد. خروجی: **instruct model**.
- **Preference Optimization (بهینه‌سازی ترجیح):** مدل را با جفت‌های «پاسخ بهتر vs بدتر» تنظیم می‌کنی تا به سلیقه‌ی انسان نزدیک شود. روش‌ها: DPO, IPO, KTO, ORPO, SimPO (بخش ۶).
- **RL (یادگیری تقویتی) و RLVR:** مدل پاسخ تولید می‌کند و بر اساس **پاداش** به‌روز می‌شود. در **RLHF** پاداش را یک reward model (آموخته از ترجیح انسان) می‌دهد؛ در **RLVR** (Reinforcement Learning with Verifiable Rewards) پاداش را یک تابع قطعی می‌دهد (مثلاً «جواب ریاضی درست است؟»). `[اثبات‌شده: Tülu 3 2411.15124]`
- **Distillation (تقطیر):** یک مدل کوچک (student) را آموزش می‌دهی تا رفتار/خروجی یک مدل بزرگ‌تر (teacher) را تقلید کند. ارزان‌تر از آموزش مستقیم و اغلب کیفیت بالاتر از SFT معمولی. `[رایج در صنعت]`
- **Model Merging (ادغام مدل):** وزن‌های چند مدل fine-tune‌شده را ریاضی‌وار ترکیب می‌کنی (بدون آموزش مجدد) تا توانایی‌هاشان جمع شود. ابزار: `mergekit`. `[رایج در صنعت]`

### ۱.۲ کدام مسیر واقع‌بینانه است؟ (با عدد)

**محاسبه‌ی هزینه‌ی pre-training یک 7B از صفر** `[فرض من، با فرمول استاندارد]`:
قانون سرانگشتی compute: **C ≈ 6 × N × D** (N=پارامتر، D=توکن، C=FLOPs). منبع رابطه: کتاب scaling و Chinchilla `[اثبات‌شده: 2203.15556]`.
- 7B مدرن روی ۱۵T توکن: C = 6 × 7×10⁹ × 15×10¹² ≈ **۶٫۳×۱۰²³ FLOPs**.
- یک H100 در bf16 با بهره‌وری واقعی ~۴۰٪ تقریباً ۴×۱۰¹⁴ FLOP/s مفید می‌دهد `[تجربی/نامطمئن: MFU حدودی]`.
- زمان = ۶٫۳×۱۰²³ ÷ ۴×۱۰¹⁴ ≈ **۱٫۵۸×۱۰⁹ ثانیه ≈ ۴۳۷٬۵۰۰ GPU-hour**. با ۲ دلار/ساعت ≈ **~۸۷۵٬۰۰۰ دلار**. ← **غیرممکن برای فرد.**
- حتی نسخه‌ی Chinchilla-minimal (۱۴۰B توکن = ۲۰×7B): ~۴٬۰۰۰ GPU-hour (~۸٬۰۰۰ دلار) ولی مدلِ ضعیفِ under-trained تحویل می‌دهی. ← **بی‌فایده.**

**نتیجه:** `[اثبات‌شده با محاسبه]` pre-training کامل = نه. **post-training روی base باز = بله.** مسیر فارسی = در صورت نیاز **CPT سبک** روی چند میلیارد توکن فارسی (اختیاری و پیشرفته) + SFT/DPO.

**مدل کوچک مسیر A (یادگیری):** یک 30M روی ~۶۰۰M توکن (نسبت Chinchilla ۲۰:۱): C = 6×3×10⁷×6×10⁸ ≈ ۱٫۱×۱۰¹⁷ FLOPs ← **چند ده دقیقه تا چند ساعت روی یک GPU معمولی.** کاملاً شدنی و آموزنده.

### ۱.۳ جدول تصمیم: کدام تکنیک برای کدام هدف؟

| هدف تو | تکنیک درست | تکنیک اشتباه (پرهیز) |
|--------|-----------|----------------------|
| یادگیری عمیق فرایند | مسیر A: مدل کوچک from scratch | pre-train 7B from scratch |
| مدل فارسیِ دستیار | SFT روی base خوب + DPO | pre-train from scratch |
| تقویت دانش پایه‌ی فارسی | CPT سبک روی corpus فارسی | SFT تنها (دانش جدید کم اضافه می‌کند) |
| یادگیری از چت کاربر | flywheel batch (KTO/DPO) | online RL لحظه‌ای |
| استدلال ریاضی/کد | RLVR/GRPO (مقیاس بالاتر) | DPO صرف |

## ۲. انتخاب Base Model

### ۲.۱ معیارهای انتخاب (به ترتیب اهمیت برای تو)

1. **لایسنس:** آیا واقعاً «مال تو» می‌شود و تجاری/شخصی آزاد است؟ Apache-2.0 و MIT بهترین‌اند. Llama و Gemma لایسنس «community» با شرط‌وشروط دارند (بخش ۱۴).
2. **کیفیت فارسی:** درک و تولید فارسی. مدل‌های چندزبانه‌ی واقعی (Qwen, Gemma, Aya) بهتر از مدل‌های عمدتاً انگلیسی (برخی Llama/Mistral/Phi) روی فارسی‌اند. `[رایج در صنعت]`
3. **اندازه‌ی tokenizer روی فارسی (fertility):** هرچه توکن به‌ازای هر کلمه‌ی فارسی کمتر، context مفیدتر و inference ارزان‌تر (بخش ۵).
4. **context length، اکوسیستم ابزار، وجود نسخه‌ی base و instruct، و benchmarkها.**

### ۲.۳ توصیه‌ی نهایی

`[فرض یا استنتاج من]` **با Qwen3-8B شروع کن** (ارزان برای یادگیریِ pipeline post-training)، بعد به **Qwen3-14B** و در نهایت **Qwen3-32B** برو. اگر به context خیلی بلند یا multimodal نیاز داری و با لایسنس Gemma مشکلی نداری، **Gemma 3 27B** جایگزین خوبی برای رده‌ی ۲۴–۲۷B است. برای کیفیت فارسیِ محض در کارِ *غیرتجاری*، **Aya Expanse 32B** را هم به‌عنوان teacher برای distillation در نظر بگیر (ولی خروجی تجاری نساز).

## ۳. سخت‌افزار و هزینه

### ۳.۱ فرمول‌های تخمین حافظه (VRAM) — با مثال عددی

**(الف) Inference (استنتاج):** حافظه ≈ وزن‌ها + KV cache.
- وزن‌ها: `بایت/پارامتر × N`. در bf16 = ۲ بایت → **7B ≈ ۱۴GB**. در ۴-بیت (Q4) ≈ ۰٫۵ بایت → **7B ≈ ۳٫۵–۴GB** (+سربار). `[رایج در صنعت]`
- **KV cache** (حافظه‌ی توکن‌های قبلی) هر توکن = `2 × n_layers × n_kv_heads × head_dim × بایت‌دیتاتایپ`. مثال تقریبی برای یک 8B با GQA (۳۶ لایه، ۸ kv-head، head_dim=۱۲۸، bf16): ۲×۳۶×۸×۱۲۸×۲ ≈ **۰٫۱۴MB/توکن** → برای ۸k توکن ≈ **~۱٫۱GB**. `[فرض من با فرمول استاندارد]`

**(ب) Full fine-tuning با Adam (mixed precision):** به‌ازای هر پارامتر ≈ **۱۶ بایت** (۲ وزن bf16 + ۲ گرادیان + ۴ master-fp32 + ۴ Adam-m + ۴ Adam-v) + activations. `[رایج در صنعت]`
- 7B full FT ≈ **~۱۱۲GB** پایه (+activations) → عملاً چند GPU یا offload لازم است.
- 14B ≈ **~۲۲۴GB**. ← چرا تازه‌کار نباید سراغ full FT برود.

**(ج) QLoRA (کلید کار تو):** base در ۴-بیت (منجمد) + فقط adapterهای کوچک آموزش می‌بینند.
- 7B QLoRA ≈ **~۸–۱۲GB** → **روی یک کارت ۲۴GB راحت، حتی روی ۱۶GB شدنی**. `[اثبات‌شده: QLoRA 2305.14314]`
- 14B QLoRA ≈ **~۱۶–۲۴GB**؛ 32–33B QLoRA ≈ **~۲۴–۴۸GB**.

### ۴.۱ منابع داده‌ی باز (راستی‌آزمایی‌شده)

- انگلیسی باکیفیت: **FineWeb / FineWeb-Edu** (HF)، **Dolma** (AI2)، **The Pile**, **RedPajama**. `[رایج در صنعت]`

**Instruction / SFT (فارسی):**

- Preference: **UltraFeedback**, **HH-RLHF** (Anthropic). `[رایج در صنعت]`

### ۴.۲ پایپ‌لاین پاک‌سازی (ترتیب درست)

1. **استخراج و normalization فارسی:** یکدست‌سازی «ی/ك» عربی→فارسی، نیم‌فاصله، حذف اعراب اضافی، فاصله‌گذاری. (ابزار فارسی: `hazm`, `parsivar` `[رایج در صنعت]`).
2. **Language ID:** جدا کردن فارسی/انگلیسی با `fastText langID` یا `GlotLID`. `[رایج در صنعت]`
3. **Dedup (حذف تکرار):** **exact** (هش) + **fuzzy** با **MinHash/LSH**. تکرار زیاد = حفظ‌کردن طوطی‌وار و افت کیفیت. `[اثبات‌شده: رویه‌ی FineWeb/datatrove]`
4. **Quality filtering:** حذف متن کوتاه/تکراری/اسپم؛ فیلتر heuristic + classifier کیفیت (مثل روش FineWeb-Edu). `[رایج در صنعت]`
5. **PII removal:** حذف شماره تلفن، ایمیل، کد ملی، آدرس (regex + مدل NER). **قبل از هر آموزشی.** `[رایج در صنعت]`
6. **Decontamination:** حذف هم‌پوشانی داده‌ی آموزش با نمونه‌های benchmark (تا تقلب و contamination نشود). Tülu 3 روی این خیلی تأکید دارد. `[اثبات‌شده: 2411.15124]`
- **ابزارها:** **datatrove** (HF)، **NeMo Curator** (NVIDIA)، **dolma toolkit** (AI2). `[رایج در صنعت]`

### ۴.۳ ساخت داده‌ی مصنوعی (Synthetic Data) — مزیت رقابتی تو

چون داده‌ی باکیفیت فارسی کم است، داده‌ی مصنوعی برایت حیاتی است:
- **Self-Instruct** `[اثبات‌شده: 2212.10560]` — از خود مدل می‌خواهی دستور+پاسخ جدید بسازد، بعد فیلتر می‌کنی.
- **Evol-Instruct** (WizardLM) `[اثبات‌شده: 2304.12244]` — دستورها را مرحله‌به‌مرحله «پیچیده‌تر» می‌کنی (عمق، محدودیت، استدلال).
- **Distillation از مدل قوی‌تر** — با یک مدل بزرگ باز (مثلاً Qwen3-235B یا Llama بزرگ) جواب‌های مرجع فارسی تولید می‌کنی و روی مدل کوچکت SFT می‌کنی.
- **Rejection sampling** — چند جواب تولید می‌کنی، بهترین را (با reward model یا LLM-judge) نگه می‌داری و بقیه را دور می‌ریزی؛ همان‌ها می‌شوند داده‌ی SFT. `[اثبات‌شده: رویه‌ی Llama/Tülu]`

**ریسک‌های داده‌ی مصنوعی `[مهم]`:**
- **Model collapse** — اگر فقط روی خروجی مدل‌ها (نسل‌به‌نسل) آموزش بدهی، تنوع از بین می‌رود و کیفیت افت می‌کند. `[تجربی/نامطمئن، شواهد رو به رشد]` → همیشه داده‌ی انسانی/واقعی را هم نگه دار.
- **تکرار سبک و bias معلم** — مدل لحن و خطاهای معلم را ارث می‌برد.
- **محدودیت لایسنس خروجی مدل‌های تجاری `[مهم، حقوقی]`** — شرایط استفاده‌ی برخی مدل‌های بسته، آموزشِ «مدل رقیب» با خروجی‌شان را منع می‌کند. برای ساخت داده‌ی مصنوعی **از مدل‌های open-weight با لایسنس مجاز** (Qwen Apache-2.0 و…) استفاده کن تا دردسر حقوقی نداشته باشی. (بخش ۱۴) `[رایج در صنعت]`

## ۵. Tokenizer و معماری

### ۵.۱ چرا tokenizer برای فارسی حیاتی است؟

**Tokenizer** متن را به واحدهای کوچک (token) می‌شکند. معیار **fertility** = میانگین تعداد توکن به‌ازای هر کلمه. هرچه بیشتر، بدتر:
- fertility بالا یعنی یک جمله‌ی فارسی توکن‌های بیشتری می‌گیرد → context مفید کمتر، inference کندتر و گران‌تر، و یادگیری سخت‌تر. `[رایج در صنعت]`
- tokenizerهای عمدتاً انگلیسی (مثل نسل اول Llama با vocab ~۳۲k) روی فارسی fertility بالایی دارند (اغلب هر کلمه چند توکن، چون کاراکتر-به-کاراکتر می‌شکنند). Qwen و Gemma با vocab بزرگ‌تر (~۱۵۰k–۲۶۲k) فارسی را بهتر پوشش می‌دهند. `[تجربی/نامطمئن — خودت اندازه بگیر]`
- **اقدام عملی:** قبل از انتخاب base، یک پاراگراف فارسی را با `len(tokenizer.encode(text))` روی چند مدل بشمار و fertility را مقایسه کن. این یک تست ۵ دقیقه‌ای است و تصمیم base model را روشن می‌کند.

### ۵.۲ آیا vocabulary را گسترش بدهم؟

- **گسترش vocab** = افزودن توکن‌های پرتکرار فارسی به tokenizer و بزرگ‌کردن embedding matrix، بعد CPT برای یادگیری embedding جدید. **PersianMind** دقیقاً همین کار را کرد (۱۰٬۰۰۰ توکن فارسی روی LLaMA2). `[اثبات‌شده: 2401.06466]`
- **ریسک:** توکن‌های جدید embedding تصادفی دارند؛ بدون CPT کافی، کیفیت افت می‌کند. کار پیشرفته است. `[رایج در صنعت]`
- **توصیه‌ی من `[فرض من]`:** اگر base خوبی با vocab چندزبانه (Qwen/Gemma) انتخاب کنی، **در شروع نیازی به گسترش vocab نداری**. این را بگذار برای فاز پیشرفته‌ی مسیر B، فقط اگر fertility فارسی واقعاً مشکل‌ساز شد.

### ۵.۳ معماری مدرن (کاربردی، نه نظری)

- **RoPE** (Rotary Position Embedding) `[اثبات‌شده]` — جای‌گذاری موقعیت با دوران؛ پایه‌ی اکثر مدل‌های امروزی. امکان گسترش context را می‌دهد.
- **GQA** (Grouped-Query Attention) `[اثبات‌شده]` — چند query head یک key/value head مشترک دارند → KV cache و حافظه‌ی inference بسیار کمتر، با افت کیفیت ناچیز. تقریباً استاندارد شده.
- **RMSNorm** — نرمال‌سازی ساده‌تر و پایدارتر از LayerNorm. `[رایج در صنعت]`
- **SwiGLU** — تابع فعال‌سازی FFN که کیفیت را بالا می‌برد. `[اثبات‌شده]`
- **MoE** (Mixture of Experts) — فقط بخشی از پارامترها برای هر توکن فعال می‌شوند → ظرفیت زیاد با هزینه‌ی محاسبه‌ی کم. پیچیده برای آموزش؛ فعلاً فقط *استفاده* کن، نساز. `[رایج در صنعت]`
- **Sliding Window Attention** — توجه محلی برای کاهش هزینه در context بلند (Mistral). `[رایج در صنعت]`
- **Long-context extension (YaRN و…)** `[اثبات‌شده]` — تکنیک‌هایی برای بردن context از مثلاً 8k به 128k با تنظیم RoPE، معمولاً با کمی fine-tune.

### ۵.۴ مسیر A: معماری و hyperparameter مدل کوچک (پیشنهاد عددی)

برای یادگیری، یک GPT کوچک «decoder-only» بساز `[فرض من، سبک nanoGPT/CS336]`:

| پارامتر | مقدار پیشنهادی |
|---------|----------------|
| پارامترها | ~۳۰M (مثلاً d_model=۳۸۴، لایه=۶، head=۶، context=۲۵۶–۵۱۲) |
| vocab | BPE خودت‌ساخته روی داده‌ی فارسی+انگلیسی، ~۸k–۱۶k |
| توکن آموزش (Chinchilla ~۲۰:۱) | ~۶۰۰M توکن |
| optimizer | AdamW، lr ~۳e-۴، warmup + cosine decay |
| batch | هر چه VRAM اجازه داد + gradient accumulation |
| precision | bf16 |

**محاسبه‌ی compute:** C ≈ 6×۳×۱۰⁷×۶×۱۰⁸ ≈ **۱٫۱×۱۰¹⁷ FLOPs** → روی یک GPU معمولی **چند ده دقیقه تا چند ساعت**. ارزان و کاملاً آموزنده. بعد یک SFT کوچک رویش بزن تا کل چرخه را لمس کنی.

## ۶. آموزش (Training Stack)

### ۶.۱ Pre-training / Continued Pre-training

- **Learning rate schedule:** `[رایج در صنعت]`
  - **Cosine decay** با warmup: استاندارد کلاسیک.
  - **WSD** (Warmup-Stable-Decay): lr ثابت می‌ماند و فقط در آخر افت می‌کند؛ برای ادامه‌دادن آموزش و افزودن داده انعطاف‌پذیرتر است (رایج در مدل‌های جدید مثل MiniCPM/OLMo). `[تجربی/رایج]`
- **Batch size بزرگ** (با gradient accumulation)، **bf16** (یا **fp8** روی H100 برای سرعت، ولی پایداری‌اش ظریف‌تر است `[تجربی]`).
- **Data mixing:** نسبت زبان‌ها/حوزه‌ها را عمداً تنظیم کن (مثلاً x٪ فارسی، y٪ انگلیسی، z٪ کد). نسبت‌ها روی توانایی نهایی اثر مستقیم دارند. `[رایج در صنعت]`
- **Replay (ضد فراموشی):** در CPT، بخشی از داده‌ی قدیمی/عمومی را نگه دار تا **catastrophic forgetting** (فراموشیِ فاجعه‌بار دانش قبلی) رخ ندهد. `[رایج در صنعت]`

### ۶.۲ SFT: full در برابر PEFT

**PEFT** (Parameter-Efficient Fine-Tuning) یعنی فقط بخش کوچکی از پارامترها را آموزش بده:
- **LoRA** `[اثبات‌شده]` — ماتریس‌های کوچک low-rank به لایه‌ها اضافه می‌کنی؛ base منجمد می‌ماند. سبک و سریع.
- **QLoRA** `[اثبات‌شده: 2305.14314]` — LoRA روی base کوانتایزشده‌ی ۴-بیت (NF4). کم‌حافظه‌ترین؛ **انتخاب پیش‌فرض تو**.
- **DoRA** — تجزیه‌ی وزن به بزرگی+جهت؛ گاهی کمی بهتر از LoRA، کمی کندتر. `[تجربی/نامطمئن]`
- **rsLoRA** — مقیاس‌دهی اصلاح‌شده‌ی LoRA برای rankهای بالا؛ در rank بزرگ پایدارتر. `[تجربی]`
- **full FT** — همه‌ی وزن‌ها؛ بهترین کیفیت بالقوه ولی گران (بخش ۳). فقط با چند GPU.

**تنظیمات کلیدی SFT:**
- **rank (r):** از **r=۱۶ یا ۳۲** شروع کن (alpha اغلب = ۲×r). rank بالاتر = ظرفیت بیشتر + ریسک overfit. `[رایج در صنعت]`
- **target modules:** معمولاً روی لایه‌های attention + MLP (`q,k,v,o,gate,up,down`). `[رایج در صنعت]`
- **Packing:** چند نمونه‌ی کوتاه را در یک sequence بچین تا GPU هدر نرود (مراقب نشت attention بین نمونه‌ها باش؛ ابزارهای خوب خودکار جدا می‌کنند). `[رایج در صنعت]`
- **Loss masking روی پاسخ:** loss فقط روی توکن‌های assistant. `[رایج در صنعت]`
- **Epochs:** معمولاً **۱–۳ epoch**. بیشتر = overfit و «طوطی‌شدن». با eval کنترل کن. `[رایج در صنعت]`

### ۶.۳ Preference Optimization: کِی کدام؟

| روش | ایده | نیاز به reference model؟ | چه موقع؟ |
|-----|------|---------------------------|-----------|
| **DPO** `[اثبات‌شده]` | یادگیری مستقیم از جفت (بهتر/بدتر) بدون reward model | بله | **پیش‌فرض؛ از این شروع کن** |
| **IPO** | اصلاح DPO برای کم‌کردن overfit به ترجیح | بله | وقتی DPO روی داده‌ی کم overfit می‌کند |
| **KTO** `[اثبات‌شده]` | فقط برچسب **خوب/بد تکی** (نه جفت) لازم دارد | بله | **وقتی فقط 👍/👎 داری ← دقیقاً حالت flywheel** |
| **ORPO** `[اثبات‌شده]` | SFT و preference را **یکجا** انجام می‌دهد (بدون مرحله‌ی جدا) | خیر | وقتی می‌خواهی pipeline ساده و یک‌مرحله‌ای باشد |
| **SimPO** `[اثبات‌شده: 2405.14734]` | reference-free؛ در گزارش‌ها از DPO بهتر شده (تا +۶٫۴ AlpacaEval2) | **خیر** | وقتی حافظه کم است یا reference دردسر است |

> **توصیه‌ی قطعی `[فرض من]`:** با **DPO** شروع کن (بیشترین مستندات و ابزار). برای **فیدبک کاربران** که اغلب 👍/👎 تکی است، **KTO** گزینه‌ی طبیعی است. **SimPO/ORPO** را به‌عنوان آزمایش بعدی نگه دار. برای هر کدام، تفاوت را با eval خودت بسنج، نه با ادعای بلاگ‌ها.

### ۶.۴ RLVR / GRPO (استدلال)

- **GRPO** (Group Relative Policy Optimization) `[اثبات‌شده]` — نسخه‌ای از RL که به‌جای reward model آموخته، از **پاداش قابل‌تأیید** (درست/غلط بودن جواب) استفاده می‌کند؛ چند جواب تولید و نسبت به میانگین گروه مزیت را حساب می‌کند. ستون فقرات **DeepSeek-R1** و مرحله‌ی سوم **Tülu 3**. `[اثبات‌شده: 2411.15124]`
- **کاربرد:** ریاضی، کد، منطق — جایی که می‌شود درستی را خودکار چک کرد.
- **آیا در مقیاس تو عملی است؟** `[فرض من]` در شروع **نه**. RLVR پیچیده، پرهزینه و بی‌ثبات‌تر از SFT/DPO است و به تابع پاداش و زیرساخت نیاز دارد. **بگذار برای فاز ۶ (مقیاس‌دهی)**، فقط اگر هدفت استدلال ریاضی/کد باشد و قبلش SFT+DPO را درست کرده باشی.

### ۶.۵ Distillation و Model Merging

- **Distillation:** با یک مدل بزرگ باز، داده‌ی باکیفیت (یا توزیع توکن‌ها) تولید کن و روی مدل کوچک SFT بزن. ارزان‌ترین راه برای بالا بردن کیفیت فارسی. `[رایج در صنعت]`
- **Model Merging با `mergekit`** `[رایج در صنعت]`:
  - **SLERP** — درون‌یابی کروی بین دو مدل.
  - **TIES** — حل تداخل علامت پارامترها هنگام ادغام چند مدل.
  - **DARE** — هرس تصادفی + بازمقیاس‌دهی دلتاها قبل از ادغام.
  - کاربرد عملی: مثلاً مدلِ «خوب در فارسی» را با مدلِ «خوب در کد» ادغام کنی، **بدون آموزش مجدد**. ارزان و گاهی شگفت‌انگیز.

## ۷. چرخه‌ی یادگیری از چت کاربران (Data Flywheel) ← هدف اصلی تو

### ۷.۱ حقیقت صادقانه: مدل‌های تجاری «چطور» از چت یاد می‌گیرند؟

`[رایج در صنعت + فرض من]` برخلاف تصور رایج، مدل‌های تجاری **لحظه‌ای و مستقیم** از هر پیام یاد نمی‌گیرند. چیزی که واقعاً اتفاق می‌افتد:
1. گفتگوها (با رضایت) **لاگ** می‌شوند.
2. **سیگنال کیفیت** جمع می‌شود (👍/👎، اینکه کاربر دوباره پرسید یا نه، ویرایش کرد یا نه).
3. دوره‌ای، یک **دیتاست جدید** از این‌ها ساخته و **فیلتر** می‌شود.
4. مدل در **batchهای زمان‌بندی‌شده** دوباره post-train می‌شود (SFT/DPO/RLHF)، نه آنلاین.
5. مدل جدید **ارزیابی** و اگر بهتر بود، **تدریجی** منتشر می‌شود.

### ۷.۲ چرا online learning مستقیم خطرناک است؟ `[رایج در صنعت]`

- **Data poisoning:** کاربر بدخواه عمداً داده‌ی سمی تزریق می‌کند تا مدل را خراب کند (نمونه‌ی تاریخی: ربات‌هایی که در ساعت‌ها منحرف شدند).
- **Drift:** توزیع ورودی‌ها جابه‌جا می‌شود و مدل بی‌ثبات می‌شود.
- **Catastrophic forgetting:** به‌روزرسانی روی داده‌ی جدید، دانش قبلی را پاک می‌کند.
- **حریم خصوصی:** مدل ممکن است داده‌ی شخصیِ یک کاربر را حفظ و به دیگری **لو بدهد** (memorization).
- **بی‌قابلیتِ rollback و ارزیابی:** وقتی لحظه‌ای یاد می‌گیری، نمی‌توانی قبل از انتشار بسنجی یا به عقب برگردی.

> **قانون من `[فرض من]`:** **هیچ‌وقت online per-message آموزش نده.** همیشه **batch + gate + rollback**.

### ۷.۳ معماری پیشنهادی: بهبود مداومِ batch-wise (۸ مرحله)

```
[چت کاربر] → (۱) لاگ با consent → (۲) حذف PII/ناشناس‌سازی →
(۳) سیگنال کیفیت → (۴) فیلتر و dedup → (۵) ساخت جفت preference/داده SFT →
(۶) آموزش دوره‌ای (هفتگی) SFT/DPO/KTO → (۷) eval با regression gate →
(۸) انتشار canary/A-B → [مانیتور] → (در صورت افت) rollback
```

1. **لاگ‌گیری با رضایت:** صریح از کاربر اجازه بگیر؛ گفتگوهای بدون consent وارد آموزش نشوند. برچسب‌گذاری منبع.
2. **ناشناس‌سازی PII:** قبل از ذخیره‌ی آموزشی، نام/تلفن/ایمیل/کد ملی را حذف یا جایگزین کن.
3. **سیگنال‌های کیفیت:** 👍/👎، regenerate (نشانه‌ی نارضایتی)، **ویرایش کاربر روی پاسخ** (سیگنال طلایی = پاسخ درستِ موردنظر کاربر)، طول/ادامه‌ی مکالمه، و در صورت امکان **LLM-as-judge** یا یک **reward model** کوچک.
4. **فیلتر و dedup:** حذف تکراری، اسپم، toxic، و نمونه‌های کم‌اطمینان.
5. **ساخت داده:** از 👍 و ویرایش‌ها نمونه‌ی **SFT** بساز؛ از جفت «👍 در برابر 👎 روی همان prompt» جفت **preference** برای DPO؛ از سیگنال باینریِ تکی داده‌ی **KTO**.
6. **آموزش دوره‌ای:** مثلاً هفتگی، QLoRA + (DPO یا KTO). **همیشه مقداری داده‌ی پایه/قدیمی را replay کن** تا forgetting نشود.
7. **Regression gate (حیاتی):** مدل جدید را روی **golden set + benchmarkها** بسنج؛ **اگر روی هر متریک کلیدی بدتر شد، منتشر نشود.** این دروازه از سقوط تدریجی جلوگیری می‌کند.
8. **انتشار تدریجی:** اول **canary** (٪ کمی از ترافیک) یا **A/B test**؛ متریک‌های زنده را ببین؛ در صورت افت، **rollback** فوری به نسخه‌ی قبل.

### ۷.۴ دفاع در برابر حمله‌ها و خرابی‌ها `[رایج در صنعت]`

- **Data poisoning:** فیلتر کیفیت + anomaly detection روی داده‌ی ورودی + سقف سهم هر کاربر در هر batch + بازبینی انسانیِ نمونه‌ای (human-in-the-loop) روی داده‌ی مشکوک.
- **Prompt injection در داده‌ی آموزشی:** متنی که «دستور» به مدل می‌دهد (مثل «از این به بعد چنین باش») را تشخیص بده و پاک کن؛ محتوای کاربر را به‌عنوان *داده* ببین نه *دستور*.
- **Bias feedback loop:** اگر فقط روی چیزی که کاربر خوشش می‌آید آموزش بدهی، مدل به سمت **sycophancy** (چاپلوسی) و bias تقویت‌شونده می‌رود → عمداً داده‌ی متنوع و «درستِ ناخوشایند» را هم نگه دار؛ متریک تنوع را رصد کن.
- **Reward hacking:** مدل یاد می‌گیرد به‌جای «خوب بودن»، سیگنال پاداش را گول بزند (مثلاً جواب طولانی چون 👍 بیشتر می‌گیرد). → متریک‌های ضدطول، regularization، و بازبینی انسانی.
- **Sycophancy:** گرایش به تأیید نظر کاربر حتی وقتی غلط است. → در eval عمداً سؤال‌های «تله» بگذار و پاسخ‌های چاپلوسانه را جریمه کن.

### ۷.۵ RAG و Memory: مکمل fine-tuning (کِی کدام؟)

- **RAG** (Retrieval-Augmented Generation): به‌جای حفظ‌کردن دانش در وزن‌ها، هنگام پاسخ، متن مرتبط را از یک پایگاه بازیابی و به prompt اضافه می‌کنی.
- **Memory کوتاه‌مدت:** تاریخچه‌ی همین گفتگو (در context).
- **Memory بلندمدت:** حقایق کاربر را در یک store (مثلاً vector DB) نگه می‌داری و در گفتگوهای بعد بازیابی می‌کنی.

| نیاز | راه‌حل درست |
|------|------------|
| دانشِ **به‌روز/حقایق خاص** (قیمت، سند، FAQ) | **RAG** (نه fine-tune — دانش سریع کهنه می‌شود) |
| **سبک، لحن، رفتار** فارسیِ دستیار | **fine-tune (SFT/DPO)** |
| **به‌خاطر سپردن ترجیح کاربر** بین جلسات | **Memory بلندمدت** (store، نه وزن‌ها) |
| مهارت/استدلال جدید | **fine-tune / RLVR** |

> `[فرض من]` قانون سرانگشتی: **حقیقت‌ها را با RAG بده، رفتار را با fine-tune یاد بده، ترجیح شخصی را در memory نگه دار.** هر سه مکمل‌اند، رقیب نیستند. برای شروعِ ارزان و کم‌ریسک، **RAG + memory** اغلب بیشتر از fine-tune ارزش می‌دهند.

### ۷.۶ حقوق و حریم خصوصی (اصول کاربردی، نه مشاوره‌ی حقوقی)

`[رایج در صنعت — این مشاوره‌ی حقوقی نیست؛ برای تصمیم جدی با حقوق‌دان مشورت کن]`
- **رضایت صریح (consent):** قبل از استفاده‌ی گفتگو برای آموزش، اجازه بگیر و امکان **opt-out** بده.
- **حداقل‌سازی داده:** فقط چیزی را که لازم است نگه دار؛ حذف PII پیش از آموزش.
- **شفافیت:** به کاربر بگو داده‌اش چطور استفاده می‌شود و چقدر نگه داشته می‌شود (retention policy).
- **حق حذف:** امکان پاک‌کردن داده‌ی کاربر به‌درخواست او (اصل سبک GDPR).
- **تفکیک محیط:** داده‌ی خام کاربر را جدا، رمزنگاری‌شده و با دسترسی محدود نگه دار؛ داده‌ی آموزشیِ ناشناس‌شده را جدا.

## ۸. ارزیابی (Evaluation-Driven Development)

> **اصل بنیادین `[فرض من، رویه‌ی حرفه‌ای]`:** **قبل از شروع آموزش، eval بساز.** بدون معیار سنجش، نمی‌فهمی مدل بهتر شد یا بدتر — و data flywheel بدون regression gate خطرناک است. «آنچه را که اندازه نگیری، نمی‌توانی بهبود بدهی.»

### ۸.۱ لایه‌های ارزیابی

1. **Golden set شخصی (مهم‌ترین):** ۲۰۰–۵۰۰ نمونه‌ی دستیِ فارسی از کارهایی که مدلت *باید* خوب انجام دهد (سؤال‌های واقعی کاربرانت، لحن موردنظر، موارد لبه و «تله»). این **سنجه‌ی واقعی موفقیت توست**، نه benchmark عمومی.
2. **Benchmarkهای فارسی (راستی‌آزمایی‌شده که واقعاً وجود دارند):**
   - **ParsiNLU** `[اثبات‌شده: 2012.06154]` — اولین benchmark جامع NLU فارسی (reading comprehension, entailment, QA, …).
   - **Khayyam Challenge / PersianMMLU** `[اثبات‌شده: 2404.06644]` — ۲۰٬۱۹۲ سؤال چهارگزینه‌ای از ۳۸ تکلیف.
   - **FarsEval-PKBETS** `[اثبات‌شده: 2504.14690]` — ۴٬۰۰۰ پرسش چندفرمتی (چندگزینه‌ای/کوتاه/تشریحی).
   - **FaMTEB** `[اثبات‌شده]` — benchmark embedding فارسی (مرتبط اگر RAG/retrieval می‌سازی؛ مدل Hakim رویش SOTA شد).
   - و یک benchmark نسبتاً جدیدِ ارزیابی LLMهای open-source روی فارسی (arXiv 2510.12807) `[اثبات‌شده]`.
3. **Benchmarkهای عمومی (عمدتاً انگلیسی — برای کنترل عدم‌افت):**
   - **MMLU** (دانش عمومی چندرشته‌ای)، **GSM8K** (ریاضی مدرسه)، **HellaSwag** (عقل سلیم)، **IFEval** (پیروی از دستور)، **MT-Bench** و **Arena-Hard** (کیفیت چت با داوری)، **Chatbot Arena** (رتبه‌بندی انسانی زنده). `[رایج در صنعت]`

### ۸.۲ LLM-as-a-judge: روش درست و bias ها

استفاده از یک LLM قوی برای نمره‌دادن به پاسخ‌ها (ارزان‌تر از انسان). ولی bias دارد `[اثبات‌شده: ادبیات MT-Bench]`:
- **Position bias:** به پاسخ اول/دوم بی‌دلیل نمره‌ی بیشتر می‌دهد → **جای A/B را جابه‌جا کن و میانگین بگیر**.
- **Verbosity bias:** پاسخ طولانی‌تر را بهتر می‌پندارد → طول را کنترل/جریمه کن.
- **Self-preference bias:** قاضی به سبک خودش نمره‌ی بیشتر می‌دهد → از قاضیِ **متفاوت** با مدل تحت آزمون استفاده کن.
- **Calibration:** روی یک نمونه، نمره‌ی قاضی را با **داوری انسانی** مقایسه کن تا بفهمی چقدر قابل‌اعتماد است.

### ۸.۳ تشخیص مشکلات پنهان

- **Contamination (آلودگی):** اگر داده‌ی آموزش شامل نمونه‌های benchmark باشد، نمره‌ها دروغین بالا می‌روند. → **decontamination** (بخش ۴.۲) + نگه‌داشتن یک test set کاملاً خصوصی.
- **Overfitting:** نمره روی train بالا ولی روی golden set پایین → epoch کمتر، داده بیشتر/متنوع‌تر، regularization.
- **Forgetting:** بعد از fine-tune، benchmark عمومی افت کرد → replay داده‌ی عمومی، lr کمتر، یا LoRA به‌جای full FT.
- **Safety و Hallucination:** مجموعه‌ای از promptهای حساس/تله بساز و نرخ پاسخ ناامن و توهم‌زده را بسنج (بخش ۱۴).

### ۸.۴ ابزارهای ارزیابی `[رایج در صنعت]`

- **lm-evaluation-harness** (EleutherAI) — استاندارد طلایی برای benchmarkهای آکادمیک.
- **lighteval** (Hugging Face) — سبک و منعطف.
- **inspect-ai** (UK AI Safety Institute) — برای eval ساختارمند و safety.
- **promptfoo** — برای تست رفتار و رگرسیون روی promptها (عالی برای golden set شخصی و CI).

## ۱۳. بخش خلاقانه و اورجینال

> همه‌ی ایده‌های زیر `[فرضیه‌ی اثبات‌نشده]` هستند — تحلیل مستقل من، نه نقل از منبع. هرجا حدس می‌زنم چیزی قبلاً منتشر شده، صریح گفته‌ام. این‌ها را مثل فرضیه‌ی علمی ببین: باید با baseline و ablation آزمایش شوند.

### ایده‌ی ۱ — استخراج ترجیح از ویرایش کاربر (Edit-Signal Preference Mining)
- **مسئله:** داده‌ی preference فارسی کمیاب است؛ ولی وقتی کاربر پاسخ مدل را **ویرایش** می‌کند، یک سیگنال طلایی تولید می‌شود که اغلب دور ریخته می‌شود.
- **شهود:** «پاسخ ویرایش‌شده‌ی کاربر» = chosen، «پاسخ اصلی مدل» = rejected. فاصله‌ی ویرایش، شدتِ ترجیح را می‌گوید.
- **الگوریتم:** (۱) لاگ (prompt, پاسخ مدل, پاسخ ویرایش‌شده). (۲) اگر edit-distance نرمال‌شده در بازه‌ی [آستانه‌ی پایین, بالا] بود (نه خیلی کم=نویز، نه کامل=بازنویسی) جفت بساز. (۳) وزن جفت = تابعی از فاصله. (۴) DPO/KTO وزن‌دار.
- **چرا ممکن است کار کند:** ویرایش انسانی سیگنال مستقیمِ «چه چیزی درست‌تر بود» است، بسیار تمیزتر از 👍/👎.
- **ریسک‌ها:** کاربر برای سلیقه ویرایش می‌کند نه درستی؛ sparsity؛ bias به سمت کاربران فعال.
- **طراحی آزمایش:** baseline = DPO روی داده‌ی عمومی؛ متریک = win-rate روی golden set؛ ablation = با/بدون وزن‌دهی فاصله، و حذف ویرایش‌های خیلی‌کوچک.
- **هزینه‌ی مقیاس کوچک:** بسیار کم؛ فقط لاگ ویرایش + چند صد جفت کافی است.
- **ارتباط با کارهای موجود:** به «learning from human edits» و RLHF با سیگنال ضمنی نزدیک است؛ احتمالاً در جایی بررسی شده، ولی به‌طور خاص برای فارسی و در حلقه‌ی flywheel شخصی، کمتر.

### ایده‌ی ۲ — KTO با دروازه‌ی اطمینان برای فیدبک نویزی (Confidence-Gated KTO)
- **مسئله:** 👍/👎 کاربران نویزی و سوگیرند؛ KTO خام روی برچسب‌های غلط آموزش می‌بیند.
- **شهود:** به هر برچسب یک **وزن اطمینان** بده و نمونه‌های کم‌اطمینان را کم‌اثر کن.
- **الگوریتم:** اطمینان هر نمونه = ترکیبی از: (الف) پایداری کاربر (آیا این کاربر معمولاً سازگار رأی می‌دهد؟)، (ب) توافق چند سیگنال (👍 + ماندن در گفتگو + نبودِ regenerate)، (ج) توافق یک LLM-judge سبک. سپس loss KTO را در این وزن ضرب کن؛ زیر آستانه → به صف بازبینی انسانی.
- **چرا ممکن است کار کند:** یادگیری با برچسب نویزی با reweighting اثبات‌شده بهتر می‌شود؛ اینجا سیگنال‌های ارزان اطمینان را می‌سازند.
- **ریسک‌ها:** تخمین اطمینان خودش نویزی؛ خطر تقویت سوگیریِ کاربرانِ «قابل‌اعتمادِ» هم‌فکر.
- **طراحی آزمایش:** baseline = KTO بی‌وزن؛ متریک = کیفیت golden + نرخ سوگیری؛ ablation = حذف هر منبع اطمینان جداگانه.
- **هزینه:** کم؛ فقط چند سیگنال و یک ضریب در loss.
- **ارتباط:** noisy-label learning و sample reweighting شناخته‌شده‌اند؛ ترکیب خاص برای KTO/flywheel احتمالاً کمتر مستند است.

### ایده‌ی ۳ — LoRA پیوسته با لنگرِ Replay و تثبیت دوره‌ای (Replay-Anchored Continual LoRA)
- **مسئله:** در flywheel هفتگی، آموزش مکرر باعث **forgetting** و بی‌ثباتی می‌شود.
- **شهود:** هر هفته یک LoRA جدید روی (داده‌ی تازه + بافر replay) آموزش بده، و دوره‌ای چند LoRA را با **TIES-merge** در base تثبیت کن؛ یک جریمه‌ی نزدیکی (KL) به مدلِ مستقرِ قبلی نگه‌دار.
- **الگوریتم:** (۱) بافر replay را با پوششِ eval پر کن (نمونه‌هایی که مدل قبلاً بلد بود). (۲) آموزش LoRAی هفته با loss = وظیفه + λ·KL به مدل قبلی. (۳) هر N هفته: merge آداپترها (TIES/DARE) → base جدیدِ تثبیت‌شده. (۴) regression gate قبل از هر انتشار.
- **چرا ممکن است کار کند:** replay + regularizer (شبیه EWC) forgetting را کم می‌کند؛ merge به‌جای انباشت آداپتر، drift را مهار می‌کند.
- **ریسک‌ها:** انتخاب λ و اندازه‌ی بافر حساس؛ merge ممکن است توانایی تازه را رقیق کند.
- **طراحی آزمایش:** baseline = fine-tune متوالی ساده؛ متریک = (کیفیت تازه) و (حفظ قدیمی) هم‌زمان؛ ablation = حذف replay / حذف KL / حذف merge.
- **هزینه:** متوسط؛ نیازمند نگه‌داری بافر + منطق merge.
- **ارتباط:** EWC، experience replay، model souping و merging همگی موجودند؛ ترکیب‌شان در یک حلقه‌ی تولیدیِ LoRA-محور، مهندسیِ ارزشمند است (نه لزوماً نظریه‌ی نو).

### ایده‌ی ۴ — ترکیب داده‌ی تطبیقیِ آگاه به Fertility برای فارسی (Fertility-Aware Adaptive Mixing)
- **مسئله:** نسبت ثابت فارسی/انگلیسی/کد بهینه نیست و فارسی به‌خاطر fertility بالا «گران‌تر» است.
- **شهود:** نسبت ترکیب را **در حین آموزش** و بر اساس «بهبود eval به‌ازای هر توکن» تنظیم کن، با توجه به اینکه هر توکن فارسی چقدر اطلاعات حمل می‌کند.
- **الگوریتم:** یک **bandit** روی حوزه‌ها بگذار؛ پاداش هر حوزه = کاهش loss روی eval آن حوزه ÷ توکن مصرف‌شده (هزینه‌ی fertility لحاظ شود)؛ نسبت نمونه‌گیری دوره‌ای به‌روزرسانی شود.
- **چرا ممکن است کار کند:** داده‌ای که بیشترین بهبود به‌ازای هزینه را می‌دهد، بیشتر دیده می‌شود؛ منابع به سمت فارسیِ کم‌پوشش می‌رود.
- **ریسک‌ها:** بی‌ثباتی bandit؛ overfit به eval؛ فراموشی حوزه‌های «ارزان ولی لازم».
- **طراحی آزمایش:** baseline = نسبت ثابت و نسبت متناسب با حجم؛ متریک = eval چندحوزه‌ای؛ ablation = با/بدون جمله‌ی fertility در پاداش.
- **هزینه:** متوسط؛ نیازمند eval حین آموزش.
- **ارتباط:** به **DoReMi** و online data mixing بسیار نزدیک است؛ افزوده‌ی من فقط جمله‌ی fertility و تمرکز فارسی است — پس **novelty محدود**، ارزش عمدتاً عملی.

### ایده‌ی ۵ — بوت‌استرپِ reward از خودسازگاری + یادگیری فعال (Self-Consistency Reward Bootstrapping)
- **مسئله:** reward model و LLM-judge فارسیِ خوب نداری؛ داوری انسانی گران است.
- **شهود:** برای هر prompt، k پاسخ نمونه بگیر؛ **خودسازگاری** (توافق پاسخ‌ها) + یک judge کوچکِ کالیبره روی golden انسانی تو، یک پاداش ارزان می‌سازد؛ جایی که مدل مطمئن نیست (پراکندگی بالا) را به **بازبینی انسانی** بفرست.
- **الگوریتم:** (۱) k پاسخ. (۲) خوشه‌بندی/رأی‌گیری برای سازگاری. (۳) نمره = ترکیب سازگاری + judge سبک. (۴) اگر عدم‌قطعیت بالا → صف انسانی (active learning). (۵) از نمرات، داده‌ی preference/rejection-sampling بساز.
- **چرا ممکن است کار کند:** self-consistency در استدلال اثبات‌شده کمک می‌کند؛ active learning بودجه‌ی انسانی را جایی خرج می‌کند که بیشترین ارزش را دارد.
- **ریسک‌ها:** روی سؤال‌های ذهنی/خلاق سازگاری بی‌معنی است؛ خطر تقویت «اکثریتِ غلط».
- **طراحی آزمایش:** baseline = judge تنها؛ متریک = همبستگی با داوری انسانی + کیفیت نهایی؛ ablation = حذف active learning / حذف self-consistency.
- **هزینه:** کم‌تا‌متوسط (k برابر inference).
- **ارتباط:** self-consistency، RLAIF و active learning همگی موجودند؛ ترکیب برای ساخت reward ارزانِ فارسی، مهندسیِ کاربردی است.

### ایده‌ی ۶ — ارتقای حافظه به وزن‌ها (Memory→Weights Promotion Ladder)
- **مسئله:** چه چیزی باید در RAG/memory بماند و چه چیزی در وزن‌ها «جا بیفتد»؟ تصمیم دستی ناکارآمد است.
- **شهود:** یک **نردبان ارتقا** بساز: حقایق/مهارت‌هایی که **مکرر و در طول زمان معتبر** بوده‌اند از memory به وزن‌ها (با distillation دوره‌ای) «ترفیع» می‌گیرند؛ بقیه در RAG می‌مانند.
- **الگوریتم:** (۱) هر آیتم memory شمارنده‌ی «استفاده‌ی موفق» و «اعتبارسنجی» دارد. (۲) آیتم‌هایی که از آستانه گذشتند و با eval سازگارند، به داده‌ی SFT تبدیل می‌شوند. (۳) distillation شبانه فقط روی آیتم‌های «تثبیت‌شده». (۴) regression gate؛ شکست = آیتم به memory برمی‌گردد.
- **چرا ممکن است کار کند:** دانش پایدار در وزن‌ها ارزان‌تر و سریع‌تر از بازیابی مکرر است؛ دانش ناپایدار در memory انعطاف می‌ماند — بهترین هر دو دنیا.
- **ریسک‌ها:** تثبیتِ زودهنگامِ غلط؛ پیچیدگی مهندسی؛ خطر forgetting هنگام distillation.
- **طراحی آزمایش:** baseline = RAG ثابت؛ متریک = دقت + latency + هزینه؛ ablation = آستانه‌های مختلف ارتقا.
- **هزینه:** متوسط‌تا‌بالا (نیازمند حسابداری memory + distillation دوره‌ای).
- **ارتباط:** به memory در «generative agents»، continual learning و knowledge editing نزدیک است؛ «نردبان ارتقای gate-شده» زاویه‌ی نسبتاً تازه‌ای است، ولی ادعای novelty قطعی نمی‌کنم.

14. **online learning مستقیم در flywheel.** نشانه: drift/poisoning. رفع: batch + gate + rollback.
15. **catastrophic forgetting بعد fine-tune.** نشانه: افت دانش عمومی. رفع: replay، lr کم، LoRA.
16. **نادیده‌گرفتن لایسنس مدل/داده.** نشانه: مشکل حقوقی بعدی. رفع: بخش ۱۴.۲.
17. **endpoint بدون auth.** نشانه: سوءاستفاده/هزینه. رفع: کلید API + rate limit (بخش ۹.۴).
18. **اعتماد کامل به agent (API/عدد/لایسنس).** نشانه: کد توهمی، آمار جعلی. رفع: verify خودت (بخش ۱۰.۶).

### ۱۴.۳ Safety پایه و red-teaming ساده `[رایج در صنعت]`

- **مجموعه‌ی safety eval بساز:** promptهای حساس فارسی (خشونت، خودآزاری، اطلاعات خطرناک، محتوای غیرقانونی) و بسنج مدل چطور پاسخ می‌دهد.
- **Red-teaming دستی:** خودت/دوستانت عمداً سعی کنید مدل را به پاسخ بد وادار کنید (jailbreak، prompt injection، نقش‌بازی). نتایج را به داده‌ی safety تبدیل کن.
- **تعادل:** هم از پاسخ‌های ناامن پرهیز کن، هم از **over-refusal** (رد کردن بی‌دلیلِ سؤال‌های بی‌خطر) که تجربه را خراب می‌کند.
- **در flywheel:** محتوای toxic کاربر نباید وارد داده‌ی آموزش شود؛ فیلتر toxicity بگذار.
- **شفافیت با کاربر:** بگو این یک مدل است و ممکن است اشتباه/توهم کند؛ در حوزه‌های حساس (پزشکی/حقوقی/مالی) هشدار بده و از دادنِ مشاوره‌ی قطعی پرهیز کن.

| اصطلاح | معنی کوتاه |
|--------|-----------|
| **Pre-training** / پیش‌آموزش | آموزش اولیه روی متن خام با پیش‌بینی توکن بعدی |
| **CPT** / پیش‌آموزش ادامه‌دار | ادامه‌ی pre-training روی داده‌ی حوزه/زبان خاص |
| **SFT** / تنظیم نظارت‌شده | آموزش روی جفت دستور→پاسخ خوب |
| **RLHF** | یادگیری تقویتی از بازخورد انسانی |
| **RLVR** | RL با پاداش قابل‌تأیید (درست/غلط خودکار) |

| **PEFT** | تنظیم کارآمدِ پارامتر (فقط بخش کوچک آموزش می‌بیند) |
| **Tokenizer / fertility** | شکننده‌ی متن به توکن / توکن به‌ازای هر کلمه |
| **Context length** | طول متنی که مدل یک‌جا می‌بیند |
| **GQA / RoPE / RMSNorm / SwiGLU / MoE** | اجزای معماری مدرن (بخش ۵.۳) |
| **KV cache** | حافظه‌ی کلید/مقدارِ توکن‌های قبلی هنگام تولید |
| **Quantization (GGUF/AWQ/GPTQ/FP8)** | کاهش دقت عددی برای صرفه‌جویی حافظه/سرعت |
| **Distillation / تقطیر** | آموزش مدل کوچک برای تقلید مدل بزرگ |
| **Model merging / ادغام** | ترکیب ریاضیِ وزن چند مدل (mergekit) |
| **Data flywheel** | چرخه‌ی بهبود مدل از داده‌ی کاربران |
| **RAG** | تولید تقویت‌شده با بازیابی (دانش از بیرونِ وزن‌ها) |
| **LLM-as-judge** | استفاده از یک LLM برای نمره‌دادن به پاسخ‌ها |
| **Regression gate** | دروازه‌ای که مانع انتشار مدلِ بدترشده می‌شود |
| **Canary / A-B / rollback** | انتشار تدریجی / آزمون مقایسه‌ای / بازگشت به نسخه‌ی قبل |
| **Catastrophic forgetting** | فراموشیِ دانش قبلی پس از آموزش جدید |
| **Replay** | تکرار داده‌ی قدیمی برای جلوگیری از فراموشی |
| **Decontamination** | حذف هم‌پوشانی داده‌ی آموزش با benchmark |
| **Loss masking** | محاسبه‌ی loss فقط روی توکن‌های پاسخ |
| **Packing** | چیدن چند نمونه در یک sequence برای بهره‌وری |
| **Reward hacking / Sycophancy** | گول‌زدن پاداش / چاپلوسیِ مدل |
